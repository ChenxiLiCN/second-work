# V14 分阶段性能诊断

日期：2026-09-08。本轮只增加诊断与验证，不改变相似度、核心判定、簇/角色输出、离线索引或在线参数。没有将诊断版本当成新的提速算法。

结论：应优先验证当前候选缓冲内的边状态复用，而不是继续只优化剩余完整邻域交集。Yelp 的状态读取累计近似 6.60 s，见证计数约 3.22 s，而剩余列表/位图/流式交集约 0.47 s；IMDB 也有明显的状态读取开销。这些为有扰动诊断估计，不是严格可加的原生耗时分账。

## 1. 测量方法

保留原 V14 二进制 `experiments/profile_v14/bri_query_v14.exe`，同时测试：

- `exclusion`：当前源码关闭诊断的 V14。
- `profile`：邻域侧诊断组，测候选生成、左邻域激活、底层判定、见证界、见证计数、列表/位图/流式交集。
- `profile_control`：控制流程诊断组，测边状态读取、精确判定入口、边证书表查询/插入/扩容、并查集查找与合并。

两组诊断使用相同 V14 算法，编译到独立程序中；普通查询程序没有热路径诊断计时。将并查集递归查找提取为内部 helper，以免把递归及合并内的查找时间重复计入“独立 find”。其路径压缩、按秩合并及处理顺序保持不变。

候选、激活、扩容、完整交集路径按调用直接计时；其余高频操作按独立伪随机序列以约 1/256 概率抽样，累计调用数并估算包含子调用的时间。每次运行记录抽样 seed。

首次未分组的探索计时还存在扩容被抽样后放大的问题，因此最终将扩容移出抽样插入范围、单独全量计时。`pilot/` 日志仅保留测量方法的演进，不用于最终结论。

每轮输出连续两次空时钟调用的平均间隔。`inclusive_ms` 是原始包含时间，`clock_adjusted_ms` 是按抽样数量扣除空时钟间隔后的近似估计；不逐样本截断，避免额外正偏。`sampling_se_ms` 只反映抽样不确定性，不包括编译布局、缓存干扰和时钟校正误差。低于时钟分辨率的小项不能精确解释。

**这些是诊断估计，不是无扰动的原生耗时。父项包含子项，不能全部相加。** 例如 state 包含其证书查询；exact 包含激活、阈值计算、底层判定和证书维护；底层判定包含见证界，见证界包含见证计数。两个诊断组来自不同运行，更不能拼成严格等于总时间的饼图。

## 2. 总时间与诊断开销

每种模式三次独立进程运行，偶数轮反转执行顺序，取中位数；未清空操作系统缓存。在线总时间仍包括加载 BRI、临时 FLI、查询、簇/角色输出和进程退出。

| 数据集 | 保存的原 V14 | 当前关闭诊断 | 邻域诊断组 | 控制流程诊断组 |
|---|---:|---:|---:|---:|
| Movies | 171.318 ms | 183.701 ms | 203.261 ms | 180.580 ms |
| IMDB | 2,945.291 ms | 2,928.675 ms | 3,248.427 ms | 3,129.109 ms |
| Yelp | 21,148.500 ms | 21,134.532 ms | 21,654.504 ms | 22,790.846 ms |

相对当前关闭诊断版本，Yelp 两组额外耗时约 2.5% / 7.8%，IMDB 约 10.9% / 6.8%。因此不能将诊断开销称作零，也不对细分数字作高精度解释。Movies 本身仅百毫秒级且波动明显，不作为本轮排序瓶颈的主要证据。原 V14 与当前关闭诊断版本在 IMDB/Yelp 基本一致，未观察到算法层面的提速。

本轮不重新构建 HINSCAN 基线，也不重新测离线索引，因为目标是定位 V14 内部瓶颈而非申报新的加速比。此前完整基线与索引时间见 V14 试验报告。

```powershell
experiments/benchmark_v13.ps1 -Datasets movies,imdb_legacy,yelp -Modes v14,exclusion,profile,profile_control -Repeats 3 -ExperimentRoot experiments/profile_v14 -RunName final
experiments/summarize_profile_v14.ps1
```

## 3. 分阶段诊断结果

固定查询仍为 Movies/IMDB：A-M-D-M-A、ε=0.5、μ=5；Yelp：U-R-B-R-U、ε=0.9、μ=5。

### 无新增诊断的主阶段

保存的原 V14 中，Yelp 三轮的临时 FLI 构建中位数为 874.092 ms，剪枝阶段 1,633.570 ms，核心聚类 17,339.000 ms，非核心归属 780.790 ms，总在线 21,148.500 ms。独立阶段中位数不要求精确相加等于总时间中位数。核心阶段约占总时间 82%；当前查询的主要瓶颈不是临时 FLI 构建。

IMDB 对应 FLI 构建 70.745 ms，核心聚类 2,312.180 ms，总在线 2,945.291 ms，同样应优先研究聚类内部。

### 查询内细分近似时间

下表先对同一轮的各阶段累计，再取三轮中位数，使用空时钟校正值；没有把来自不同运行的父子项拼成总时间。

| 操作 | IMDB | Yelp |
|---|---:|---:|
| 边状态读取 state（包含内部证书查询等） | 1.19 s | 6.60 s |
| 候选生成（包含过滤、去重和排序） | 0.69 s | 3.49 s |
| 见证计数（见证界的子项） | 未启用 | 3.22 s |
| 左邻域激活 | 0.029 s | 1.77 s |
| 列表/位图/流式交集路径（含右邻域按需获取） | 0.60 s | 0.47 s |
| 并查集显式 find | 0.052 s | 0.46 s |
| 并查集 unite（含内部 find） | 0.0046 s | 0.027 s |

补充包含关系：Yelp 见证界整体约 4.19 s，包含上表 3.22 s 的计数；所有边证书表 get 约 4.74 s，横跨 state 与 exact 两个入口，不是可再加上的独立项；证书插入约 0.16 s，扩容约 0.145 s。表明应重点关注重复**读取**，不能把证书表扩容说成主瓶颈。

### 直接计数证据

Yelp 核心阶段 state 调用 85,732,038 次，exact 入口及底层判定请求各 8,491,975 次，证书表 get 共 94,224,013 次。状态读取次数约为底层判定请求的十倍。不同阶段对同一候选重复检查是从源码可定位的工作，减少这部分开销有比继续微调完整交集更直接的依据。

核心阶段 state 校正估计中位数为 6,243.33 ms，其原始抽样标准误中位数约 31.63 ms；见证计数分别为 3,154.79 / 29.44 ms。这只说明抽样排序较稳定，不能消除诊断扰动及校正系统误差。

## 4. 下一步候选改动（本轮未实施）

第一优先级是验证**单个顶点处理期间的局部边状态复用**。当前同一批候选在初始过滤、核心确认、已知相似边合并、剩余核心连接扫描中多次调用 `state`，每次可能再次访问全局边证书表。可以尝试让当前候选缓冲携带本轮已知状态，并在执行精确检查后更新它，从而减少重复哈希探测。

正确性约束：全局边证书仍保留供其他顶点访问；每个候选去重；本顶点处理中产生的新状态必须同步到局部缓冲；核心密度、邻居计数更新、跨核心分量连接、非核心多簇归属不能省略。先做原处理顺序不变的最小改动，不同时混入近似过滤或更换聚类算法。

第二个独立消融方向是**先检查安全的核心连通性跳过条件，再查边状态**，避免对已知同一核心分量内、且不再需要密度确认的边做无用查询。只对已有 pSCAN 逻辑最终必然跳过的情况重排条件，不能由“同簇”推断任意两点直接相似，更不能跳过非核心密度判定所需的贡献。

这些仍是待验证假设，不能按状态查询次数直接推算最终加速倍数。即使局部查询开销消失，也不能保证达到数量级目标；后续再考虑更大粒度的候选批量省略。
